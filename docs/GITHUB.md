# GitHub: one app is the only door to your repositories

The hub holds a GitHub App's private key, and nothing else holds a GitHub credential. When a worker fetches, git asks the hub for a password, and gets a read-only installation token that works for **one repository** (the one the agent's item lands in), which GitHub expires **after an hour**. When a worker pushes, the push goes to the hub, which passes on only `nuworq/*` branches with a write token of its own that the worker never sees. Each mint goes on the item's record: which agent, which item, which repository, until when. The token itself is never stored, and a token that writes is never shown to an agent.

## 30 seconds

1. In the hub, as an owner: **Connect an agent → Create GitHub App**. Then install the app on the repositories your projects live in.
2. Start workers as usual (`nuworq worker` / `nuworq run`). Pushes over `https://github.com/…` just work.
3. Turn on the ruleset below so that only pull requests change `main`, whoever pushes.

## 5 minutes: set it up

**Create the app in one click.** In the hub's UI, an owner opens **Connect an agent** and clicks **Create GitHub App** (or opens `/api/github/app/new`; add `?org=<name>` to create it in an organization). The page posts GitHub's app manifest, with exactly the permissions below and the hub's webhook and return addresses. Confirm on GitHub, and you're sent back to the hub. The hub trades GitHub's one-time code for the app's id, private key and webhook secret, saves them to `<data dir>/github-app.json` (mode 0600, readable only by the hub's user), and uses the app at once. `serve` picks the file up on every start, with no environment variables. This works on a single hub. With `--workspaces`, the host sets the app up as below.

**Or by hand** (the fallback, and the way for workspaces hubs). On GitHub, go to Settings → Developer settings → **GitHub Apps** → New GitHub App (for an organization: its Settings → Developer settings). Then:
- Name: e.g. `nuworq-<your-org>`. Homepage URL: your hub's public address.
- Webhook: **Active**, URL `https://<hub>/api/hooks/github-app`, content type `application/json`, and a long random **Webhook secret** (give the hub the same one, below). Subscribe to **Issues**, **Issue comment**, **Pull request**, **Pull request review**, **Check suite**, **Check run** and **Dependabot alert** (installation events always come). This one webhook serves every project on every repository the app is installed on, so no project needs a webhook or secret of its own. A hub GitHub can't reach (localhost) leaves it off, and each project's own webhook still works (see DEPLOY.md, "GitHub: pull requests and CI on items").
- Repository permissions: **Contents: read & write**, **Pull requests: read & write**, **Checks: read**, **Issues: read & write**, **Dependabot alerts: read**, **Metadata: read**. Organization permissions: **Members: read**, so the hub can check that whoever installs it on an organization is its admin before binding it to their workspace. Nothing else, and no account permissions.
- Where can it be installed: *Only on this account*.
- Create it, note the **App ID**, and under *Private keys* generate one (a `.pem` download).

**Install it** (left menu: Install App) on the repositories your projects live in. Choose *Only select repositories*.

**On a shared hub (`--workspaces`), each organization installs the app from inside itself.** Set the app's *Setup URL* to `https://<hub>/api/github/installed` (with *Redirect on update*), and tick **Request user authorization (OAuth) during installation**; set its *Callback URL* to the same address. Under *Client secrets*, generate one, and give the hub the app's **Client ID** and that secret as `NUWORQ_GITHUB_APP_CLIENT_ID` and `NUWORQ_GITHUB_APP_CLIENT_SECRET` (an app the hub created in one click keeps them in its saved file). An owner or steward opens `/w/<org>/api/github/install`, which sends them to GitHub's install page with a signed state naming the organization. When GitHub sends them back, the hub trades the authorization code for the installer's token and binds the installation to the organization only if GitHub lists it among that person's installations (`GET /user/installations`) and the installation is on their own account, or on an organization where GitHub says they are an active admin (`GET /user/memberships/orgs/<org>`): the redirect's `installation_id` alone can be forged, and that list also shows installations a person can merely read. Without the client id and secret, or without a code, nothing is bound and the hub says why. The first binding stands. From then on, the hub mints tokens for an organization's workers, mirrors, pull requests and issues only from installations bound to it. Another organization naming the same repository gets a 403 telling it to install the app for itself. Organizations on a shared hub also never use the hub's own SSH identity or a path on its disk: a mirror is fetched with a bound installation's token, or with the organization's own deploy key under `keys/<org>/`, or not at all.

**Give the hub the app** (by hand only; environment variables win over the saved file), then restart the hub:
```bash
NUWORQ_GITHUB_APP_ID=123456
NUWORQ_GITHUB_APP_KEY_FILE=/etc/nuworq/github-app.pem   # chmod 600, owned by the hub's user
NUWORQ_GITHUB_APP_SLUG=nuworq-acme                      # its name in github.com/apps/<slug>: install links in errors
NUWORQ_GITHUB_APP_WEBHOOK_SECRET=…                      # the app's webhook secret: deliveries to /api/hooks/github-app
```
(`NUWORQ_GITHUB_APP_KEY` takes the PEM itself, if a file doesn't suit.) In the systemd unit, put them in an `EnvironmentFile=` readable only by the hub's user.

**The app's webhook.** GitHub signs each delivery to `/api/hooks/github-app` with the app's webhook secret, and the hub refuses any it can't verify (401) or any delivery at all when it has no secret (404). A delivery goes to every project that has the repository it is about (an installation event: any repository it lists), and is handled exactly like a delivery to that project's own webhook. The one-click app gets its secret from GitHub and turns its webhook on, subscribed to the events above, when the hub's address is public. On a shared hub, a delivery reaches only the organization its installation is bound to; one from an installation bound to nobody changes nothing. So a project on GitHub needs nothing but the app installed on its repository: its issues come in, pull requests and checks reach its items, and GitHub's merge marks the work done.

**Issues come in as proposals.** Through the app's webhook, with nothing to set up. Without it, in the project's webhook (DEPLOY.md), also tick **Issues** and **Installation repositories**. When the app is installed on a project's repository, each open issue there becomes a proposal linked to it (`look` shows the issue). Pull requests are skipped. After that, every issue opened, reopened or labelled comes in through the webhook. The hub posts one comment on each issue with the item's link. When the item is done, its issues close: a pull request landing says `Fixes #N` for each, so GitHub closes them on merge. For any other landing (a fast-forward of `main`, or an issue GitHub left open), the hub's sweep closes the issue itself with one more comment, naming the item and the commit on `main`. It only closes an issue that is still open, and it waits 2 minutes after a merge, so a `Fixes` close is never doubled. If GitHub fails, the item stays done, the failure goes on its record once, and the next sweep tries again. Closing an issue drops its item if nobody has started on it; if the work is under way, the item only gets a note. Reopening brings the same item back. To take only some issues, set a label in the project settings (`issue_label`, e.g. `nuworq`); adding that label to an issue later brings it in. `POST /api/p/<project>/github/resync` (an owner or steward) lists the open issues again; ones already in are skipped.

**Dependabot alerts come in as work.** When the app is installed on a project's repository, each open Dependabot alert there becomes one item, and after that every alert GitHub creates or reopens comes in through the webhook (without the app, tick **Dependabot alerts** in the project's webhook). The hub writes the item itself: the title says the package must reach the first patched version (`lodash is at 4.17.21 or later in acme/api (GHSA-…, high)`), the summary holds the package and ecosystem, manifest, vulnerable range, advisory id and link, and severity, and done means the package resolves to the patched version on main (manifest and lockfile), the tests pass, and GitHub shows the alert fixed. So it is ready work wherever the project lets agents start shaped proposals. Severity sets priority: critical and high are *now*, medium *soon*, low *later*. An alert with no patched version comes in as a proposal with the three ways forward (replace the package, accept the risk and dismiss the alert, or wait). When GitHub marks an alert fixed or dismissed, its item is dropped if nobody has started on it; otherwise it gets a note and the work goes on. A reopened alert brings a dropped item back. If its item already landed (the vulnerable version came back), it comes in as one new item that fixes the landed one, and the alert follows the new item from then on. No routine alert creates a "needs you" entry. `POST /api/p/<project>/github/resync` lists the open alerts again too. The project's GitHub dialog (`GET /api/p/<project>/github`) shows, per repository, whether alerts come in. If they can't, it gives the steps: an installation from before this permission existed must accept it (open `https://github.com/settings/installations/<id>`, or `https://github.com/organizations/<org>/settings/installations/<id>`, click **Review request**, then **Accept new permissions**), and a repository with Dependabot alerts off must turn them on (`https://github.com/<owner>/<repo>/settings/security_analysis`, **Enable** next to *Dependabot alerts*). The dialog asks GitHub again when opened (at most every 30 seconds), so the line turns green once that's done, and the open alerts come in then. Neither problem stops issues or other webhooks.

**Asking the reporter.** An agent on an item that came from an issue can `ask` with `to: "reporter"`. The hub posts the question on the issue as a comment that @-mentions its author, and the item parks like any blocking question. Their reply comes back through the app's webhook (or, without it, tick **Issue comments** in the project's webhook). The reporter's next comment on that issue answers the question (`answered_by` is `github:@login`), the item returns to ready, and the agent gets the answer at its next checkin. Comments by anyone else, by apps (the hub's own), edits and redelivered webhooks change nothing. With no reply after the project's `reporter_wait` (hours, default 48, in the project settings), the question shows in "needs you", and your answer works as usual. A reply after that goes on the item's record as a comment, not a second answer. On an item with no issue, or a hub without the app, the ask fails with a hint to ask the human. If GitHub refuses the comment, the sweep posts it again.

**Workers.** `nuworq worker` sets git up in the worker's own environment (`GIT_CONFIG_*`, no config file changes). `nuworq git-credential --project <p> --as <worker>` is its only credential helper: the person's own (the macOS keychain, `gh`, any other) are reset, `git@github.com:` addresses fetch over HTTPS, and `SSH_AUTH_SOCK` is unset, so no key of the person's is used. The helper answers GitHub with a read-only token for the project's repository, and the hub with the worker's name and agent token.

**Pushes go through the hub** (`pushInsteadOf`, to `<hub>/api/git/github.com/<owner>/<repo>.git`). The hub reads the ref updates at the head of the push: it passes on only `refs/heads/nuworq/*` branches, for the repository of the item the worker holds, with a write token it minted for that repository. A push to `main`, a tag, any other branch or a deletion is refused, and git shows why (`! [remote rejected] … (workers never push main: the hub lands accepted work itself)`). Both go on the item's record, as `pushed_via_hub` and `push_refused`. The pushes are smart HTTP, so the worker's git needs nothing extra. A runner's worker gets no land job that would push `main` (work on origin without the app): a session or the operator lands that. With no checkout of a project on the machine, `nuworq run` and `nuworq worker` clone it over HTTPS into the first folder in `NUWORQ_REPOS` (else beside the repo they start in). The clone uses a read-only token the hub mints for that project's repository (`git-credential --project`, on the record as `credential` with purpose `clone`); without an App they skip the project with the clone command, as before. A clone whose origin is `git@github.com:…` (SSH) uses SSH keys instead; switch it to HTTPS to go through the app: `git remote set-url origin https://github.com/<owner>/<repo>.git`.

## The recommended ruleset on `main`

With the app as the only writer, a ruleset makes sure `main` changes only through a pull request with green checks. That holds even for the app's own tokens, so an agent can push `nuworq/*` branches and open pull requests, but a push to `main` is refused.

Repository → Settings → Rules → **Rulesets** → New branch ruleset:
- Name `main`, Enforcement **Active**, Target: *Include default branch*.
- **Bypass list: empty.** Don't add the app.
- Rules: **Restrict deletions**, **Block force pushes**, **Require a pull request before merging** (1 approval if humans review, 0 if agents do), **Require status checks to pass** (your CI job, e.g. `test`).

**Landing through a pull request.** A hub with the app lands accepted work in GitHub repositories it has no checkout of through a pull request. On accept, the hub opens the PR as the app (head: the item's branch, base: `main`; the body links the item and names its builder, model, reviewer and evidence, plus `Fixes #N` for each open issue linked to the item, and when it was created with `issue: N`) and turns on auto-merge (squash). The item waits in landing, linked to the PR, and no agent gets a land job for it. When GitHub merges it after the checks pass, the `pull_request` webhook (the app's, or the project's own) marks the item done (a `landed` event naming the PR). Closing the PR unmerged sends the item back to ready with a note. If the branch isn't on origin yet, an agent gets a land job that only pushes it; then the hub opens the PR. If GitHub refuses the PR, the refusal goes on the record (`pr_failed`) and the item becomes an ordinary land job. If auto-merge can't be turned on (it is off in the repository's settings), the PR is still opened, and merging it by hand lands the item the same way. A PR with nothing left to wait for (no required checks, or they already passed) gets no auto-merge from GitHub ("Pull request is in clean status"): the hub squash-merges it at once, and the item is done. Since no webhook may reach the hub, it also looks at every landing item's open PR itself, at most once a minute: one that is ready with no auto-merge gets merged (a refusal goes on the record once, as `pr_merge_failed`, and it tries again); one GitHub merged lands its item as the merged webhook would; one closed without merging leaves the item in landing as a land job; one that conflicts with `main` becomes a land job to rebase the branch and push it with `--force-with-lease`, after which the PR carries on. Without the app, a session or the operator lands by fast-forwarding `main` (`git push origin <branch>:main`), as before; a runner's workers don't, since they push only `nuworq/*` branches.

## 30 minutes: details

- **What a token can do.** A worker's: contents read and metadata read. The hub's own, for passing a worker's pushes on: contents write, pull requests write, checks read and metadata read. Each is for one repository, for one hour. It is minted when git first asks, not at claim time, so claims that never fetch or push cost nothing. Git asks on every fetch and push. The same agent, item, repository and kind reuse the token until 5 minutes before it expires: one mint and one event, not one per git command. The reused token is kept in the hub's memory only, never in its database.
- **When there is no token.**
  - The agent holds no item: 409, "claim one, then fetch"; a push through the hub, 403.
  - The project isn't on GitHub: the hub says so.
  - The app isn't installed on the repository, was uninstalled, or is suspended: 424, *"The nuworq GitHub App isn't installed on acme/api (or was uninstalled), so the hub can't give out tokens for it"*, with the install link. The refusal goes on the item's record too.
  - A hub without an app answers 404, and the helper steps aside so git uses whatever else is set up.
- **The hub's own mirrors.** A hub with no checkout of a project keeps a mirror of its repository. With the app installed there, the hub fetches the mirror over HTTPS with a token of its own: contents read and metadata read, on that one repository. The hub keeps it in memory and reuses it until 5 minutes before it expires. The token reaches git only through the environment, never in a command line, the mirror's config, or a log. Without an app, or for a repository that isn't on GitHub, the hub fetches over SSH with deploy keys, as before ([DEPLOY.md](DEPLOY.md)). If GitHub refuses the app a token there (not installed, uninstalled, suspended), the project shows it under *worth knowing* with the install link, and the hub uses a deploy key if it has one. It asks GitHub again every 5 minutes, and the notice clears once a token comes.
- **On the record.** Each mint is an event on the item, `credential`, with `{agent, item, repo, expires_at, token, write}`, where `token` is the name of the agent token that asked (null on a hub without login) and `write` says it was the hub's own, for a push. Refusals are `credential_refused`.
- **The worker's sandbox.** A Claude Code worker's shell runs in Claude Code's sandbox, set from `--settings` so no settings file in the repository can loosen it: it writes only in its worktree, the checkout's `.git` and temp; it can't read `~/.ssh`, `~/.nuworq`, cloud or `gh` credentials; and it reaches only the hub, GitHub, the project's package registries, and the hosts a person adds in the project's settings (`sandbox_hosts`, e.g. `api.stripe.com`). Its allowlist names the project's own commands (`npm test`, `npm run <script>`, `pytest`, `cargo test`, `go test`, …), not `node` or `python3`. opencode has no sandbox, so `nuworq worker` doesn't start it for a project with a remote.
- **Not yet.** Signing people in through the app's user authorization. On a shared hub, the installation event GitHub sends as an organization installs the app arrives before the installation is bound, so it brings no issues in; resync (`POST /w/<org>/api/p/<project>/github/resync`) brings them in after.
