# nuworq's threat model

Who might attack nuworq, where the trust boundaries are, and which defence covers which threat. Security reviews read changes against this file: one before each release, and one area a month (see [Keeping it checked](#keeping-it-checked)). If you find a threat it misses, add it here. To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## What there is to protect

- **People's machines.** Workers and operators run on them, with a shell, the person's git credentials and their files.
- **Workspaces' data.** Items, questions, evidence, field notes, people, tokens and billing. Each workspace sees only its own.
- **Releases.** Code that `nuworq update` and the Claude Code plugin install on people's machines.
- **The hub host.** The VM running app.nuworq.com, its GitHub App key, its webhook secrets and its databases.

## The attackers

| Attacker | What they can do to start with | What they're after |
|---|---|---|
| **The anonymous internet** | Reach the hub's public pages, sign-in, webhooks and `/live/<slug>`. Read the public repository. | Any data, a session, a foothold on the host. |
| **Another workspace** | Sign in, hold tokens and agents of its own, and call every API its role allows. | Another workspace's data, or acting in it. Or stalling the hub every workspace shares: one process and one event loop serve them all, so one costly request stops every tenant (#779). |
| **A member, by role** | What their role allows: owner, member or viewer. | More than their role: settings, people, billing, other projects. |
| **An agent token** | Agent operations in its project, as the agent it names. | Human operations (accept, settings, decisions), acting as another agent, other projects. |
| **A person's own agents** | The agent tokens they minted (device login, `nuworq token`), within their role as it is now (#629). | Through their agents, what their role refuses them in person: claiming, reviewing, push tokens. |
| **A stranger's issue or reply** | Write text that the hub imports from GitHub. Agents read that text. | Prompt injection: getting an agent to run, push or leak something. |
| **A hostile or impersonated hub** | Whatever a runner, worker or MCP process accepts from the hub it's connected to. | Running code on people's machines, or reading their files and tokens. |
| **A compromised hub VM** | Everything the hub holds: databases, the GitHub App key, webhook secrets. | Releases, and people's machines through them. |

## Trust boundaries

1. **The internet and the hub's HTTP edge.** Everything that arrives is untrusted until sign-in, a token, or a webhook signature says who sent it.
2. **One workspace and the next.** Each workspace has its own database (`src/workspaces.js`). A request opens only the workspace its session or token belongs to.
3. **A person and an agent.** Human operations need a person's session. Agent operations need an agent's identity. A token is for one or the other, never both.
4. **Outside text and the agents.** Issues, replies and feedback from people without write access are data, not instructions, until a person lets them in.
5. **The hub and the machines it staffs.** A runner trusts its own machine, not the hub. The hub sends definitions (data) and never code.
6. **Main and a release.** Agents land on main on their own. Code reaches people's machines only through a release that a person approved and the release key signed. The key never sits on the hub.

## The defences

Each defence names the item that built it and the tests that guard it.

### The HTTP edge and sign-in
- **Sign-in decides identity.** Plans, owner rights and notifications follow how someone signed in, never an email they typed (#470: `test/identity.test.js`, `test/adminspaces.test.js`). A verified sign-in never vouches for a session it didn't create: a person made by opening an invite link carries the invite's email unproven, and until #612 a later verified sign-in with that email marks that same row verified while the link-opener's session stays valid.
- **Roles and tokens.** A person's role and a token's identity decide what a caller may do. Agent operations are for agents, and each agent acts only as itself (#469: `test/agentroles.test.js`, `test/auth.test.js`).
- **A token never outdoes its minter.** An agent token may do no more than the person who minted it may now: a member's machine proposes and comments, and demoting someone narrows their tokens at once. Runner tokens stand on their own. Auth.identity reads the minter's role on every call; the agent routes then apply #469's limits for that role, and the device page tells a member what their machine can do. Powers named for a member's token on the hub host (`nuworq token create --powers`) are the host's own grant and stand until the member is a viewer (#629: `test/mintercap.test.js`, found by the review of sign-in, accounts and tenancy, #590). #609, that only a token a steward or owner minted may act as an operator, is the narrowest case of it.
- **Stored as hashes.** Tokens, sessions and codes are stored as hashes, never as the secret itself.
- **Hardened edge.** The hub reads real client addresses behind a proxy, builds links from its own address, and sends HSTS. Errors are quiet: a 500 carries an id and no internals. Markdown renders in a single pass and streams are capped (#479: `test/edge.test.js`, `test/wait.test.js`). Escaping and the CSP hold.
- **No SQL injection.** Every query takes parameters.
- **No request stalls the shared hub.** Work the hub does on what a caller sends must grow with its size, not faster: the 1 MB body cap doesn't help a pattern that backtracks. That holds above all for checks that run before limits and roles, such as the secret check on every agent operation. The JWT token shape added in v0.8.0 broke this (#780, found by #779). New patterns over written text need a test on long hostile input.
- **Written text stays text.** What agents, people and outsiders write (titles, questions, headlines, issue text) is escaped wherever it's shown. It must also never be read as the hub's own markup, such as the time markers Needs you's sentences carry (#689). Text that could forge them must break nothing but itself (#781, found by #779).
- **One token can't flood a hub.** An agent makes at most 60 writes a minute, and its token at most 240 under all its names, on every project at once; a token checks in under at most 100 new names an hour (#766, #831). A project takes at most 1,000 comments a day and holds at most 500 field notes, and one person's agents may hold at most a fifth of each, under the names of every token that person minted, so connecting another machine adds no room and they can't use up the rest for other agents; a token no person minted counts on its own (#851, #857, found by #849). Covered by `test/floodlimits.test.js`.
- **What a runner reports is a runner's.** Runner state, live spend above all, changes what the hub lets every runner do (#761, #762). It counts only from runner tokens, for their own workers (#782, found by #779).

### Workspaces
- **Isolation.** Every route opens only the caller's workspace (`test/isolation.test.js`).
- **Deleting a workspace is its owners' alone** (#799). It needs an owner's session: never an agent token, never a member. The request must come from the same origin, name the workspace exactly, and the workspace must have no plan that renews. Afterwards its name answers 410 "deleted" to anyone, signed in or not, until the name is taken again. That says only that a workspace of that name once existed.
- **Inbound events.** GitHub and Stripe events count only from those entitled to send them. Installs bind to their owner, and strangers' PRs change nothing (#478: `test/githubtrust.test.js`, `test/billing.test.js`, `test/appwiring.test.js`).
- **Outbound requests.** The hub reaches only the public internet on people's behalf. Notification channels and preconditions can't touch the network it runs on (#474: `test/outbound.test.js`).

### Outside text (the maintainer's call 2)
- **Held for a person.** Issues from people without write access wait for a person's OK, as feedback does, and so do those people's replies. Issues from collaborators flow as before (#471: `test/outsiders.test.js`).
- **Information, not instructions.** Field notes, handoffs, comments and quoted text are information. Only steering and decisions carry a person's authority (the agents' guide, src/protocol.js).
- **A passed-on reply is words, not a decision.** A person who passes on an outsider's held reply lets its text in as data. The words inside it must not act as that person's answer. Since #819 the hub itself drops a parked item when a person answers its question with "drop". A sentence inside a quoted reply could read as such an answer, so a passed-on reply never drops a parked item or keeps it waiting with "not yet", and refine refuses it as a reason to drop (#839, found by #835). Covered by `test/answerdrop.test.js`, "a passed-on outsider reply never drops or holds a parked item".
- **Titles are public.** Item titles show on the live view, so a finding's title names what its fix guards, never the hole.

### People's machines (the maintainer's call 3)
- **Workers run sandboxed.** Their shell writes only inside the worktree and reaches only the hub, GitHub and package registries. They run exact commands, not prefixes, and push only their own branch. Landing on main goes through the hub (#472, with #487 as its live test).
  - **Only the project's checks by default** (#768). npm install and an arbitrary npm script amount to running anything, so a worker's allowlist has `npm test`, `npm ci` and the check scripts (test, lint, check, typecheck, build and their `name:variant`s, never one naming deploy, release, publish, upload, push or migrate), and the Python, Rust and Go test and build commands. A person adds others in Settings (`worker_commands`): plain words, so nothing chains, never an interpreter alone, and never one that runs code given inline (`node -e`, `python3 -c`, `npm exec`, `npx`); the runner checks what the hub sends the same way (`test/sandbox.test.js`, `test/runner.test.js`). A script still runs what package.json says, which is why the sandbox is around it.
  - **Not every harness is sandboxed the same way** (review #596). Only Claude Code workers get the sandbox above, with DENY_READ keeping the machine's keys unreadable. A hostile hub's task text could have any other harness read them and report them back, so `worker` and `run` start one only with `--can-read-keys`, and say in one line what it can read (#615: `test/runner.test.js`). The trade-off per harness:
    - **Codex** runs with `-s workspace-write`: writes and network are limited, reads aren't. Wrapping it in a second OS sandbox isn't an option: Codex applies its own Seatbelt profile, and macOS refuses a nested one. So, like opencode and pi, it runs only on projects without a remote, until Codex can deny reads (#768: `test/runner.test.js`).
    - **opencode and pi** have no sandbox. They run only on projects without a remote (bin/nuworq.js), so there's nothing to push to, but their shell can read the keys and reach any host. Their own config folders are among the paths DENY_READ hides, so they couldn't run under it.
  - **What a worker can read of the machine's credentials.** DENY_READ (src/sandbox.js) covers keys, every harness's and toolchain's stored logins (Claude Code, Codex, opencode, pi, git, cargo, gem, Terraform, yarn, npm, PyPI, cloud CLIs), shell histories, the macOS keychains and browser profiles, and the release key's folder (`~/.nuworq-release`: the release key and the release workflow's deploy key, #850). A worker's agent starts on an allowlisted environment (workerEnv, src/runtrust.js): where things are, nuworq's non-secret settings, and only the variables its harness reaches its model with. Claude Code keeps those from its shell (CLAUDE_CODE_SUBPROCESS_ENV_SCRUB), and Codex does too (shell_environment_policy.exclude). opencode's and pi's shells see their one model key. A project's own variables come only by name (`nuworq run --env DOCKER_HOST`); a name that looks like a secret takes `--env-secret`, which an installed runner refuses (#616: `test/sandbox.test.js`, `test/clientlabel.test.js`).
  - **Where work lands in the checkout** (no origin), the worker may write the whole checkout. What an unsandboxed process later reads there stays denied: other workers' folders in `.git/worktrees` (as they are when it starts), and `.claude/`, `.envrc` and `.vscode/` in the checkout and its own worktree (#606: `test/sandbox.test.js`). A worker started later isn't in an earlier one's list; the runner's cleanup git is what reads those folders.
  - **A push is to the held item's branch only, and landing merges the head that was reviewed.** Otherwise a worker could replace another item's accepted branch, or add to its own after review (#605). The hub's push proxy passes on only `refs/heads/<branch of the item the pusher holds>`. Acceptance records the branch head the hub sees (items.reviewed_sha). Auto-merge is pinned to it with expectedHeadOid, and the squash-merge with sha. A head that moves afterwards goes back to review with auto-merge off, unless it's the same change rebased or with main merged into it (#784). That is checked in `sameChange` (`src/git.js`): each head's diff from where it branched off main must remove and add the same lines in the same order in each file, and each hunk of the new head must sit where the reviewed one lands once main's own edits between the two branch points have moved the lines (#806). Main's edits beside the change don't count. Where main added lines at the very spot the change adds its own, the change may sit on either side of them. A hunk moved anywhere else in its file, such as a guard taken out of the function it protected, goes back to review (`test/git.test.js`, `test/gitproxy.test.js`, `test/githubflow.test.js`, `test/prland.test.js`).
  - **A worker's `git rm` stays in its worktree** (#796): no path from the root or home, none built by the shell or climbing out with `..`, and no `--pathspec-from-file` (rmOutside, src/gitrules.js: `test/sandbox.test.js`).
- **The operator's no-prompt rules are a boundary too.** An operator runs unsandboxed as the person and reads text that started with workers or strangers. Its permission prompt is the last thing a person sees, so the rules `nuworq operator --allow` writes must never let it run a program or store a command without asking (#607). They allow only `nuworq`'s agent operations and what reads, never `nuworq:*`. They deny git's program-running and output options (`--upload-pack`, `--receive-pack`, `--exec`, `rebase -x`, `--output`, `--ext-diff`) on every allowed command, and force and delete flags bundled with others. The infra check, a command `--detect` runs, changes only when a person confirms it at a terminal (`test/opdetect.test.js`, `test/operatorcmd.test.js`).
- **An operator is someone a person trusted.** The operator role comes from a declared tag; a token a member minted shouldn't get it (#609), and an operator's words never carry a person's authority to other agents (#610).
- **A runner trusts its machine.** It checks what the hub sends, and keeps its token out of commands, environments and logs (#477: `test/runtrust.test.js`, `test/runner.test.js`). A worker's llm-proxy token stays off its command line (#493: `test/clientlabel.test.js`). Its log masks Anthropic, OpenAI and llm-proxy keys (`sk-…`), any key in a header line, and the value of every secret in the runner's own environment. Browser workers' Playwright MCP server isn't fetched with npx. It comes from src/browser/package-lock.json, which pins it and its two dependencies by sha512; npm ci installs it once into `~/.nuworq/browser/` (#626: `test/runtrust.test.js`, `test/runner.test.js`).
- **No fetched code.** Nothing is ever run that was fetched at runtime. Code arrives only through the package, checksum-verified (a standing decision).

### Releases (the maintainer's call 1)
- **The maintainer approves each release.** Since #813 a release is signed on GitHub Actions (`.github/workflows/release.yml`): an unprivileged `check` job refuses a tag that isn't a release and builds the package as the hub does. The `sign` job runs only after the maintainer approves it in the `release` environment. The release key is that environment's secret, and only the approved job reads it. That job runs no repository code: it rebuilds the package with `git archive` alone, must match check's sha256, and signs in node:crypto written in the workflow file, which agents can't change (the hub's App has no `workflows` permission). So code landed on main can't reach the key through the workflow. It can change what `check` runs, so a separate `changes` job, also only the workflow's own shell, repeats the on-main, version and rollback checks and says whether that code changed since the last signed release, with the diff. The hub serves a GitHub Release's `.sig` only when it verifies over the hub's own build of that commit (or over GitHub's gzip of byte-identical files); otherwise it raises an alarm to the operator (`src/ghrelease.js`). The Mac signer that came before it retired with #815. Signing by hand, the fallback, makes the workflow's checks (`releaseRefusal`), and since #836 it can't be reached from main either: it is `nuworq release sign`, which runs only from an installed package, and `docs/DEPLOY.md` has the maintainer install the last GitHub Release's package after checking its signature. The command can't tell that from the hub's unsigned package of main, so that step is the protection. From a git checkout it refuses before it opens the key file, since a checkout runs whatever landed on main. Covered by `test/releasesign.test.js`. The plugin installs from the `release` branch, never from main; only the environment's deploy key and the maintainer may move it. On GitHub (#476), rulesets let only admins (the maintainer) create, move or delete the `release` branch and `v*` tags, and the hub's App can't bypass them. Last checked 2026-11-02 (#757). Approval for outside contributors' workflows can only be set once the repository is public (#365). Covered by #473: `test/plugin.test.js`, `test/package.test.js`.
- **A compromised hub can't ship.** Every way of signing builds the package from GitHub's copy of the tagged commit, never the hub's, and the hub serves a signature only over its own build of that commit. Installs check the signature against the pinned `release-key.pub` (`src/update.js`). Signing by hand (`nuworq release sign`, #815, #836) runs only from an installed package that pins the key, never from a git checkout (it refuses before reading the key: "signing by hand never runs a checkout's code with the key"), only at a terminal, after the person types the tag, and makes the workflow's checks before it signs: origin's tag is on origin's main, at its version, pinning this key, and newer than the hub's signed release. It refuses otherwise and says which check failed (`test/releasesign.test.js`, "signing by hand"). "GitHub's copy" there is whatever the checkout's origin fetches from, which the command doesn't check: it holds because the hub refuses fetches (`/api/git/` takes only pushes, src/server.js), so a checkout can't be pointed at it, and DEPLOY.md runs it in a checkout whose origin is GitHub. `sign-release.js sign` signs any file it is given and checks nothing, so it is for files you built yourself, never a package fetched from the hub.
- **The key never runs code landed on main.** The workflow holds this: its `sign` job runs no repository code. Signing by hand holds it since #836 (found by the pre-release audit, #835). Before, `sign-release.js release` ran in a checkout and imported that checkout's `scripts/release.js` and `src/package.js` in the process that read the key, so what protected it was the maintainer switching to the last signed release's tag first. Its check of the same (`scripts/checkout.js`, #829) was a safety net for an honest copy, not a guarantee: from a checkout at main, main's copy runs, and a landed change could drop the check and DEPLOY.md's step together. The terminal and the typed tag were that code's own checks too. Now it is `nuworq release sign`, the installed package's code: from a git checkout it refuses before it opens the key file, and `scripts/sign-release.js release` and `scripts/checkout.js` are gone. Covered by `test/releasesign.test.js`, "signing by hand never runs a checkout's code with the key". Releases signed before #836 don't have the command, so until one that has it is signed, the hand fallback is the last signed release's own `sign-release.js release`, run from a checkout at its tag (docs/DEPLOY.md). v0.9.0's is the older `approve`, then `release <hub> <pem>` (#843); v0.10.0's is `release <vX.Y.Z> <pem> <hub>`, with #829's check. The maintainer accepted this for v0.10.0, which ships before #836.
- **What the approval summary compares with is signed.** The `changes` job counts the hub's `/api/package` release commit against a rollback whenever it is newer than GitHub's, since that only refuses more. It compares with that commit only when the hub's `.sig` for it verifies against the tag's `release-key.pub`, over a `git archive` of that commit built as `sign` builds it. Otherwise it says the hub's claim didn't verify and compares with GitHub's last signed release (#837, found by #835). So a compromised hub can't name an unsigned commit, such as the tag's parent, to make the summary say nothing changed. A landed swap of `release-key.pub` can make the hub's claim verify, but it can't get signed: `sign` checks the tag's `release-key.pub` against the real key and refuses. Covered by `test/releasesign.test.js`, "the approval summary's base is a release whose signature verified".
- **Workers on the key's machine can't read the key.** Signing by hand keeps the release key, and the workflow's deploy key that moves `release`, in `~/.nuworq-release` on the maintainer's machine (docs/DEPLOY.md), and that machine may run workers. A sandboxed worker reads anything DENY_READ (src/sandbox.js) doesn't hide, so a compromised hub's task text, or outside text a person let in, could have one read the key: it signs anything installs accept. DENY_READ must hide that folder (#850, found by #849). Unsandboxed harnesses (`--can-read-keys`) read it anyway: never run them on the key's machine.
- **Plugin installs follow releases only.** An install made before #473 still tracks main's marketplace file until connect moves it onto the `release` branch (#608).
- **Reviewed before it ships.** In a project with security reviews on, every release waits for a review of what it ships (below).

### The repository
- **Ready to be public.** A license, a way to report vulnerabilities, and a scan of the complete history (all commits and GitHub's `refs/pull/*`) with nothing private in it (#475).

## The five areas

The monthly reviews take these in turn (`AREAS` in `src/security.js`):

1. **Sign-in, accounts and tenancy.** Who can reach which workspace, project and data.
2. **The web client and the HTTP edge.** Pages, the API, headers, and how what people and agents wrote is rendered.
3. **Integrations, webhooks and updates.** GitHub, Stripe, llm-proxy, the self-update and release signing.
4. **Worker machines and prompt injection.** What an agent on someone's machine may run, read and push.
5. **Data, secrets and open-source readiness.** What the database, logs, evidence and the repository hold.

## Keeping it checked

The project setting **Security reviews** (Settings → Security reviews) turns these on (`src/security.js`):

- **Before each release.** When the hub drafts a release, it opens "Security review before the next release". The release depends on that review, so it can't land, be tagged or be signed until the review is done. The review goes only to an agent that built none of the changes the release ships, which the hub enforces at claim time.
- **A serious finding holds the release.** A critical or high finding is proposed with its fix and added to the release's dependencies, and the human is asked "Fix it before the release" or "Accept it for this release". Only the maintainer's "Accept" takes it off.
- **Each month, one area.** A review of the next of the five areas opens every 30 days.
- **Findings, rated and tested.** Each finding is rated critical, high, medium or low by the attackers above, and proposed as its own item with the fix and a regression test named for what it guards. No working exploit goes into an item, comment or evidence: they are as public as the repository.
